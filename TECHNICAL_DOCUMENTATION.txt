1. PROJECT OVERVIEW & PROBLEM STATEMENT
--------------------------------------------------------------------------------
The "TeamSync" is a professional-grade collaboration platform designed 
to solve the "Visibility Gap" in distributed teams. In modern engineering and 
creative workflows, the challenge isn't just knowing "what to do," but knowing 
"who is doing what, by when, and under what authority."

Problem Statement:
Traditional task lists lack the security and role enforcement needed for teams. 
Information silos occur when tasks are discussed in chat but not tracked in 
a structured database, leading to missed deadlines and overlapping work.

Real-World Use Case:
A software agency managing multiple client projects simultaneously. The Admin 
(Project Manager) needs to partition data so that Developers (Members) only 
see tasks relevant to them, while ensuring that project-level destructive 
actions (like deleting a project) are strictly restricted.

3. HIGH-LEVEL SYSTEM ARCHITECTURE
--------------------------------------------------------------------------------
The system utilizes a Decoupled Architecture. The frontend is a standalone 
Single Page Application (SPA) that acts as a "thick client," handling routing 
and state locally. The backend is a "headless" JSON API.

Statelessness:
The backend is strictly Stateless. It does not store "sessions" in server memory. 
This is critical for scalability. If the user load grows, we can spin up 10 
identical server instances, and they don't need to share session data—the JWT 
provided by the client contains everything needed for authentication.

4. TECH STACK DEEP DIVE (COMPARISONS & TRADE-OFFS)
--------------------------------------------------------------------------------

A. FRONTEND: REACT (VITE)
- Selection: React was chosen for its mature ecosystem and Virtual DOM efficiency. 
  Vite replaced Create React App (CRA) due to its use of native ES modules and 
  extremely fast Hot Module Replacement (HMR).
- Trade-off: React has a steeper learning curve than Vue but offers more 
  flexibility in complex state management.

B. BACKEND: NODE.JS (EXPRESS)
- Selection: Node.js allows for a unified language (JavaScript) across the 
  stack. Express is minimalist, giving us full control over our middleware 
  pipeline.
- Comparison: Node.js is non-blocking and event-driven, making it superior 
  to Django (Python) or Rails (Ruby) for high-concurrency real-time apps.

C. DATABASE: MONGODB
- Selection: Document-oriented storage (JSON/BSON) is a natural fit for 
  web applications. 
- Trade-off: MongoDB trades ACID compliance in complex multi-document 
  transactions for massive write speeds and schema flexibility.

D. AUTH: JWT VS SESSIONS
- Choice: JWT.
- Why: Sessions require a database look-up on every single request to verify 
  the session ID. JWTs are verified in-memory by the server using a secret key, 
  drastically reducing DB load and latency.

E. STYLING: TAILWIND VS BOOTSTRAP
- Choice: Tailwind CSS.
- Why: Tailwind avoids the "generic look" of Bootstrap by providing utility 
  classes. It also optimizes the final build by "purging" unused CSS, resulting 
  in significantly smaller file sizes.

5. DETAILED FOLDER STRUCTURE EXPLANATION
--------------------------------------------------------------------------------
Modular design is the backbone of maintainability.

SERVER:
- /config: Centralizes environment-dependent setup (e.g., DB connection). 
  Problem solved: Prevents DB init logic from cluttering server.js.
- /models: The source of truth for data structure. 
  Problem solved: Enforces strict schema rules on a schema-less database.
- /controllers: Pure logic. No routing knowledge.
  Problem solved: Makes the logic reusable and unit-testable.
- /routes: Maps URLs to controllers.
  Problem solved: Provides a "Table of Contents" for the entire API.
- /middleware: Reusable security/utility functions.
  Problem solved: Dry (Don't Repeat Yourself) principle—logic like "is logged in" 
  is written once and applied everywhere.

CLIENT:
- /context: Global state (Auth).
- /api: Centralized Axios config.
- /pages: Route-level components.
- /components: Reusable UI atoms (Cards, Modals).

6. BACKEND ARCHITECTURE & MVC PATTERN
--------------------------------------------------------------------------------
We use an MVC-inspired pattern (Model-View-Controller).
- Model: Mongoose schemas representing Users, Projects, Tasks.
- View: JSON responses (in a headless API, the "View" is the data payload).
- Controller: The bridge between the request and the database.

This separation ensures "Loose Coupling." If we decide to swap MongoDB for 
PostgreSQL, we only change the Models and parts of the Controllers—the Routes 
and Middleware remain untouched.

7. DATABASE DESIGN & DATA RELATIONSHIPS
--------------------------------------------------------------------------------

RELATIONSHIPS & CARDINALITY:
1. User <-> Project (Many-to-Many):
   - A user can be a member of many projects.
   - A project can have many members.
   - Implementation: We store an array of User IDs in the Project `members` 
     field, and an array of Project IDs in the User `projects` field.
2. Project <-> Task (One-to-Many):
   - A project has many tasks.
   - A task belongs to exactly one project.
   - Implementation: Task documents contain a `projectId` reference.
3. User <-> Task (One-to-Many):
   - A user can be assigned many tasks.
   - A task is assigned to one (or zero) users.

Why NoSQL?
In a task manager, a "Task" might eventually need custom fields (e.g., story points, 
labels, subtasks). Relational databases require expensive "ALTER TABLE" 
operations and migrations. MongoDB allows us to append new fields to documents 
without breaking existing data.

8. VALIDATION STRATEGY (FRONTEND & BACKEND)
--------------------------------------------------------------------------------
Validation is not just for UX; it is a critical security layer.

A. FRONTEND VALIDATION (First Line of Defense)
- Purpose: Immediate feedback. Prevents unnecessary network requests.
- Example: Checking if email matches a regex or if password is > 6 chars 
  before the "Sign In" button becomes active.

B. BACKEND VALIDATION (Final Authority)
- Library: `express-validator`.
- Purpose: Sanitize input and enforce rules. 
- Security: Prevents NoSQL Injection and ensures that malicious users cannot 
  send oversized payloads or unexpected data types to the DB.

9. API DESIGN & ERROR HANDLING DEEP DIVE
--------------------------------------------------------------------------------
We follow REST (Representational State Transfer) conventions.

STANDARD ERROR RESPONSE:
All errors return a consistent JSON structure:
{
  "success": false,
  "message": "Human readable error",
  "errors": [ { "field": "email", "message": "Invalid email" } ] // Optional
}

HTTP STATUS CODES:
- 200 OK: Success.
- 201 Created: New resource successfully made.
- 400 Bad Request: Validation failed.
- 401 Unauthorized: JWT missing or invalid.
- 403 Forbidden: User authenticated but lacks role (e.g., Member trying to delete).
- 404 Not Found: Resource does not exist.
- 500 Internal Server Error: Unexpected crash.

10. AUTHENTICATION & SECURITY BEST PRACTICES
--------------------------------------------------------------------------------
1. Password Hashing: We never store plain text. Even if the database is 
   leaked, the bcrypt hashes take billions of years to crack.
2. JWT Risks:
   - XSS: We store tokens in localStorage for simplicity, but in high-security 
     apps, HttpOnly cookies are preferred to prevent JavaScript from reading tokens.
   - Token Theft: Short expiration times (7d) mitigate the risk of stolen tokens.
3. CORS (Cross-Origin Resource Sharing):
   - We whitelist only our frontend domain (`http://localhost:5173`). 
     This prevents other malicious websites from making requests to our API.

11. ROLE-BASED ACCESS CONTROL (RBAC)
--------------------------------------------------------------------------------
RBAC is enforced via middleware: `requireRole('Admin')`.
- Why it's important: In real-world enterprise apps, data privacy is legally 
  required. A regular employee should never see salary data or delete infrastructure. 
- Our implementation: We check the `role` field on the `req.user` object 
  (populated from the JWT) before allowing the request to reach the controller.

--------------------------------------------------------------------------------
12. FRONTEND ARCHITECTURE & STATE MANAGEMENT
--------------------------------------------------------------------------------
State Management: Context API + useReducer.
- Problem: "Prop Drilling" (passing data through 5 layers of components).
- Solution: The `AuthProvider` wraps the app, making `user` and `login` data 
  available anywhere via the `useAuth` hook.

Protected Routes:
The `ProtectedRoute` component acts as a "Gatekeeper." It checks if the 
`token` exists. If not, it uses React Router's `<Navigate />` to force the 
user back to `/login`.

13. DATA FLOW: THE REQUEST-RESPONSE LIFECYCLE
--------------------------------------------------------------------------------
Case Study: Adding a Member to a Project
1. Admin enters email and clicks "Add Member".
2. React triggers `api.put('/projects/:id/add-member', { email })`.
3. Axios Interceptor injects `Authorization: Bearer <token>`.
4. Backend `protect` middleware verifies JWT.
5. `requireRole('Admin')` middleware verifies the user is an Admin.
6. Controller finds the User by email.
7. Controller pushes the UserID to the Project's `members` array.
8. MongoDB persists the change.
9. Controller returns the updated Project object.
10. React updates the UI to show the new member's avatar.

14. EDGE CASE HANDLING
--------------------------------------------------------------------------------
1. Invalid Login: Handled by returning 401 and a clear message without 
   confirming if the email exists (security best practice).
2. Unauthorized Access: Handled by `ProtectedRoute` on frontend and `protect` 
   middleware on backend.
3. Empty Inputs: Handled by `required` attribute in HTML and `express-validator`.
4. Duplicate Users: Mongoose `unique` index on email catches this and returns 
   a specific error message.
5. Network Failures: Axios interceptors catch 500 errors and show a "Something 
   went wrong" toast to the user.

--------------------------------------------------------------------------------
15. PERFORMANCE & QUERY OPTIMIZATION
--------------------------------------------------------------------------------
1. Database Indexing: We index `email`, `projectId`, and `assignedTo`. This 
   converts O(N) collection scans into O(log N) tree lookups.
2. Lean Queries: Using `.select('-password')` reduces the amount of data 
   traveling from DB to Server.
3. Selective Population: Using Mongoose `.populate()` only for necessary fields 
   to avoid "Over-fetching."
4. React Efficiency: Using `key` props and splitting components to ensure 
   that adding a task doesn't re-render the entire sidebar.

--------------------------------------------------------------------------------
16. SCALABILITY DEEP DIVE
--------------------------------------------------------------------------------
Horizontal Scaling (Scaling Out):
Because we use stateless JWTs, our server has no "sticky sessions." We can 
put our API behind a Load Balancer (like AWS ELB or Nginx) and add more 
servers as traffic increases.

Database Scaling:
MongoDB Atlas supports "Sharding"—distributing data across multiple clusters. 
We can scale from 1,000 users to 1,000,000 users without changing our code.

20. DESIGN DECISIONS & PHILOSOPHICAL TRADE-OFFS
--------------------------------------------------------------------------------
- MongoDB vs SQL: Chose MongoDB for speed of development and flexibility. 
  Trade-off: Lack of strict relational constraints.
- Context vs Redux: Chose Context for zero overhead. Trade-off: Less granular 
  control over rendering in massive apps.
- REST vs GraphQL: Chose REST for simplicity and standard HTTP caching. 
  Trade-off: Potentially more API calls for complex nested data.
